# Agentic 동작 여부 감사 보고서

- 감사일: 2026-09-29
- 대상: `financial-disclosure-review` 현재 소스, 테스트, 저장된 평가 결과 및 체크포인트
- 질문: 이 서비스가 실제로 agentic하게 동작하는가, 아니면 규칙·키워드 탐지를 agent처럼 포장하는가?
- 종합 신뢰도: **높음(구현 판정)** / **중간(실효성 판정 — 실페이지 표본이 작음)**

아래에서 `domain/`, `graph/`, `knowledge/`, `llm/`로 시작하는 소스 경로의 기준 디렉터리는 `src/financial_disclosure_review/`이다.

## 1. 결론

**이 서비스는 agentic한 척만 하는 순수 규칙·키워드 시스템은 아니다.** 모델이 매 턴 사용할 도구와 인자를 고르고, 실행 결과 또는 거절 사유를 다시 관찰한 뒤 다음 행동을 선택하는 진짜 폐쇄 루프가 현재 코드에 세 군데 구현되어 있다.

1. 처음 보는 상품 페이지의 탐색 및 수집 규칙 작성
2. 증거 카드와 유사한 제재·분쟁 사례의 검색·열람·연결
3. 자유 서술 독자 요청을 데이터셋 필터로 변환

다만 **서비스 전체가 목표를 스스로 분해하고 실행 계획을 바꾸는 자율 에이전트는 아니다.** 상위 검토 순서는 고정 LangGraph이고, 분기와 재시도 정책도 코드가 결정한다. 분류, 증거 카드 추출, 표시방법 판단, 설명 생성 등 다수 단계는 구조화된 단발성 LLM 호출이며, 일부만 2회 검증된다. 사이트 규칙이 캐시되어 있거나 자유 서술 독자 요청이 없거나 연결 가능한 사례가 없으면 위 에이전트 루프 일부는 아예 실행되지 않는다.

따라서 가장 정확한 표현은 다음과 같다.

> **규칙·측정·LLM 판단을 결합한 고정 검토 워크플로 안에, 제한된 세 가지 하위 작업용 도구 호출 에이전트를 둔 혼합형 시스템**

“완전 자율 에이전트”라고 부르면 과장이고, “키워드 기반인데 agent인 척한다”고 단정하면 구현을 잘못 설명한다. 에이전트성은 **실재하지만 국소적이고 강하게 제한되어 있다.**

## 2. 판정 기준과 등급

본 감사에서는 agentic을 단순히 “LLM을 쓴다”가 아니라 다음처럼 구분했다.

| 수준 | 판정 기준 | 이 서비스 |
|---|---|---|
| 0 | 규칙·키워드만으로 입력→출력 | 해당하지 않음 |
| 1 | 모델 단발 호출, 도구 선택·피드백 루프 없음 | 여러 판정 노드가 이 수준 |
| 2 | 고정 워크플로가 여러 모델/도구 호출을 순서대로 실행 | 서비스 전체 오케스트레이션 |
| 3 | 모델이 관찰에 따라 도구·인자를 선택하고 결과를 받아 반복 | 페이지 탐색·사례 연결·독자 선택 |
| 4 | 상위 목표를 분해하고 실행 계획/노드 자체를 동적으로 구성 | 해당하지 않음 |
| 5 | 장기 목표·지속 메모리·폭넓은 자율 실행 | 해당하지 않음 |

**전체 서비스는 수준 2의 고정 워크플로이며, 일부 하위 모듈은 수준 3의 bounded agent다.**

## 3. 실제 agentic하다고 판단한 근거

### 3.1 모델이 실제 도구 호출을 생성한다

`llm/client.py:95-134`의 `ToolChat`은 `ChatOpenAI.bind_tools(...)`로 도구를 모델에 바인딩한다. 각 턴에서 모델 응답의 `tool_calls`를 읽고, 호출 결과를 `ToolMessage`로 대화 기록에 추가한다. 즉 다음 도구 선택은 직전 관찰 결과를 포함한 대화 상태를 보고 모델이 생성한다.

이는 코드가 미리 `inspect → probe → submit` 순서를 하드코딩한 방식과 다르다. 코드는 허용 도구와 안전 경계를 제공하지만, 특정 턴에 어떤 도구를 어떤 selector/query/filter로 호출할지는 모델 응답에서 온다.

### 3.2 페이지 탐색은 관찰→행동→피드백 루프다

- 목표와 사용 가능한 도구: `domain/product_page/discover.py:19-42`
- 최초 페이지 관찰 및 gap 생성: `discover.py:49-61`
- 모델 턴, 도구 실행, 결과 재주입, 성공 시 종료: `discover.py:62-91`
- 실제 브라우저 도구: `domain/product_page/tools.py:23-67`
- 제출한 selector와 landmark의 라이브 DOM 검증: `tools.py:242-285` 이후

모델은 `inspect_page`, `probe_selector`, `interact`, `submit_rule` 중에서 선택한다. 클릭·스크롤·동일 출처 링크 열기 후 새 evidence가 생겼는지 다시 관찰하고, 제출 규칙이 거절되면 오류를 받아 수정할 수 있다. 반복 행동, 폼/로그인/결제, 외부 출처 이동은 도구 계층이 차단한다.

저장된 실제 실행 trace도 이 구조와 일치한다.

- `f1-lotte-lasvegas`: `inspect_page → interact → inspect_page → probe_selector → submit_rule → probe_selector → submit_rule ...` 순으로 10턴을 사용하고 `완료/full_coverage`로 종료
- `f1-shinhan-revolving`: 두 번의 상호작용으로 새 evidence를 얻은 뒤 여러 차례 selector 탐색과 제출 수정을 수행했지만 19턴에서 `조사 불충분/turn_budget`으로 종료
- `f1b-kb-cardloan`: 도구가 두 상호작용을 차단했고, 모델은 이후 inspect와 submit을 반복했으나 20턴 안에 승인 규칙을 만들지 못함

이런 서로 다른 행동열은 “페이지 유형별 if/else 스크립트”가 아니라 모델 선택과 도구 피드백으로 발생한다. 다만 성공률은 §6과 같이 낮다.

### 3.3 사례 연결도 검색→열람→제안의 도구 루프다

- 에이전트 목표·규칙·도구 설명: `knowledge/linking.py:59-83`
- 도구 스키마: `linking.py:86-127`
- 검색 상태, 읽은 사례, 승인 링크를 실행별로 보존: `linking.py:134-160`
- 매 턴 모델 도구 선택과 결과 재주입: `linking.py:453-492`

모델이 자체 query와 card id를 골라 `search_cases`를 호출하고, 후보를 `read_case`로 읽은 다음 `propose_link` 또는 `finish`를 선택한다. 검색 자체는 BM25이고 embedding rerank는 선택 사항이지만, **무엇을 검색·열람·연결할지는 모델이 결정한다.**

동시에 코드는 제안된 사례가 이번 실행에서 실제 검색·열람되었는지, 페이지 인용과 사례 인용이 원문에 있는지, 판정 표현이 섞이지 않았는지를 검증한다(`linking.py:313-373`). 이 규칙은 agenticity를 대체하는 가짜 로직이 아니라 모델 행동의 신뢰 경계다.

### 3.4 자유 서술 독자 선택도 제한된 도구 루프다

- 반복 실행과 도구 결과 피드백: `domain/persona_explanation/selection.py:160-228`
- 자유 서술 요청일 때만 에이전트 호출: `selection.py:310-326`
- UUID·명시 필터·기본값은 규칙 기반 우선순위: `selection.py:281-308`, `328`

실행 기록 `f1-shinhan-revolving`에서는 모델이 한 턴에 여러 `list_values`를 호출하고, 다음 턴들에서 두 번 `count_matches`, 마지막에 `choose`를 호출해 4턴 만에 독자를 골랐다. 반면 독자 요청이 없는 실행은 `default`를 사용해 모델 루프를 생략했다.

## 4. agentic하지 않은 부분

### 4.1 상위 그래프는 고정 DAG다

`graph/build.py:27-70`에 노드와 간선이 전부 정적으로 선언되어 있다. 정상 경로는 아래 순서로 고정된다.

`preprocess → classify → evidence cards → reference cases → display → persona explanation → explanation duty → verify → report`

모델이 새 노드를 만들거나, 작업 순서를 재계획하거나, 필요 없는 단계를 생략하거나, 새로운 전문 도구를 발견하지 않는다. 분류가 범위 밖인지, 검증 실패를 재시도할지는 `graph/routes.py:9-28`의 코드 분기가 정한다.

### 4.2 재시도 계획도 코드가 정한다

`graph/retry.py:6-18`은 최대 2회, 재시도 가능한 모듈, 노드 순서를 상수로 고정한다. `plan_retry()`도 실패 모듈을 가장 앞선 허용 노드에 매핑할 뿐이다(`retry.py:39-54`). 모델이 실패 원인을 보고 전체 계획을 다시 짜는 구조가 아니다.

### 4.3 대부분의 LLM 사용은 구조화된 단발 판단이다

`llm/client.py:15-36`의 `ask()`는 스키마를 강제한 1회 호출이다. `call_ask()`는 검증 실패 시 최대 2회 재호출하지만 도구 선택 루프나 계획 수립은 없다(`llm/client.py:66-80`). 다음 영역들이 이 계열이다.

- 상품 분류
- 증거 카드 추출
- 표시방법의 일부 정성 판단
- 독자 맞춤 설명 생성
- 설명의무 판단
- 의미 보존 검사

이들을 “LLM 기반 판단” 또는 “검증된 생성”이라고 부르는 것은 맞지만, 개별 호출 자체를 에이전트라고 부르는 것은 부정확하다.

### 4.4 에이전트 루프는 조건부다

- 저장된 사이트 규칙이 유효하면 페이지 수집은 모델 호출 없이 재생된다: `domain/product_page/fetch.py:98-133`
- 자유 서술 독자 요청이 없으면 기본 필터를 쓴다: `selection.py:328`
- 증거 카드 또는 대상 상품의 사례가 없으면 사례 연결 모델을 호출하지 않는다: `knowledge/linking.py:420-435`

따라서 모든 리뷰 요청이 같은 정도로 agentic한 것은 아니다. 운영 지표에는 “이번 요청에서 어떤 에이전트 루프가 실제 실행되었는지”를 분리해 표시해야 한다.

## 5. 규칙·키워드 기반 요소 감사

규칙과 키워드는 상당히 많이 쓰인다. 그러나 현재 프로덕션 상품 분류를 키워드 카운트로 몰래 대체하거나, 고정 응답을 agent 결과처럼 꾸민 증거는 찾지 못했다.

| 영역 | 실제 방식 | 판정 |
|---|---|---|
| 상품 유형 분류 | 모델이 3단계 판단과 페이지 원문 인용을 생성하고 코드가 인용 존재를 확인. 부정 판정은 별도 모델 호출로 재확인 (`classification/classify.py:13-59`) | LLM 판단, agent loop는 아님 |
| 키워드 상품 분류 | `evaluation/suites.py:44-65`에만 있는 비교 기준선. `arm == "keyword"`일 때만 평가에서 사용 (`:68-79`) | 프로덕션 위장 로직 아님 |
| 페이지 조사 gap | 혜택·조건·경고 등의 정규식 신호 사용 (`product_page/coverage.py:18-25`) | 에이전트가 볼 후보/공백을 만드는 휴리스틱 |
| 표시방법 E02/E04/E05 | CSS/렌더링 측정값과 법정·WCAG 임계값을 코드가 판정 (`display_check/judge.py:51-80`) | 의도된 결정론적 검사 |
| 사례 검색 | 결정론적 BM25, 선택적 embedding rerank; 검색 query와 후속 열람·연결은 모델 선택 (`knowledge/linking.py:222-274`) | 규칙 도구를 사용하는 에이전트 |
| 안전·무결성 | URL, selector, 인용, 도구 인자, 위험 행동, 숫자·사실 보존을 코드로 검증 | 필요한 guardrail |
| 보고서 및 법규 매핑 | 고정 규칙과 DB 매핑 | 설명 가능성과 법률 인용 안정성을 위한 결정론적 계층 |

핵심은 **규칙의 존재 자체가 비-agentic의 증거가 아니라는 점**이다. “관찰에 따라 다음 행동을 누가 고르는가”가 기준이다. 이 서비스에서는 상위 흐름은 코드가, 세 하위 루프의 다음 도구는 모델이 고른다.

## 6. 실효성: 진짜 에이전트지만 아직 잘하는 에이전트는 아니다

### 6.1 페이지 탐색

최신 저장 결과 `eval/results/260929-101426-agent-loop.{json,md}` 기준:

- 실페이지 7개 중 `완료` 3개, `조사 불충분` 4개
- actionable gap closure 36.9%
- 허용된 상호작용 중 새 evidence가 없던 비율 28.6%
- 상호작용 차단 비율 30.0%
- 페이지당 평균 비용 약 $0.0964, 평균 약 230초

도구 루프가 실제로 움직였다는 증거인 동시에, 다양한 사이트에서 안정적으로 목표를 달성한다고 주장하기에는 부족한 결과다.

### 6.2 사례 연결

현재 linking agent를 직접 평가한 `eval/results/260929-100431-linking.json` 기준:

- AI 초안 gold 14개 중 5개 발견: recall 35.7%
- 채점 대상 링크 7개 중 false link 2개: 28.6%
- 4페이지 중 3페이지가 8턴 한도 도달
- 32회 모델 호출, 약 $0.072

이는 고정 lexical threshold보다 일부 recall을 회복했지만, 사례 연결의 품질과 종료 효율이 아직 낮다는 뜻이다. 더구나 gold는 `docs/evaluation.md:262-274`에 명시된 대로 AI 초안이며 사람 확정 라벨이 아니다.

### 6.3 비결정성과 안정성

`eval/results/260929-093006-agentic-stability-replay.md`의 3회 반복 결과:

- 증거 카드 `(kind, quote)` Jaccard: 0.365~0.533
- 카드론 gold recall: 0.75~0.917
- LOCA gold recall: 0.538~0.769
- 독자 설명 accepted unit 수: 실행마다 14~43개로 크게 변동
- 반면 코드가 확인한 fact ledger는 두 페이지에서 각각 40/40, 25/25로 안정적

즉 생성·추출 계층은 많이 흔들리며, 결정론적 검증 계층이 사실 보존의 안정성을 보완한다. 혼합 설계의 장점은 확인되지만 단일 실행의 completeness를 신뢰하기 어렵다.

### 6.4 평가 파일의 세대 혼재

`eval/agentic_eval.py`라는 이름과 달리 현재 이 파일의 사례 부분은 새 linking agent가 아니라 과거의 결정론적 `knowledge.reference.retrieve_reference_cases`를 호출한다(`eval/agentic_eval.py:50-52`, `266-273`). 현재 linking agent 평가는 별도 `eval/linking_eval.py:40`, `121-129`에 있다.

따라서 `260929-091525-agentic-replay`의 reference 수치를 현재 사례 연결 에이전트의 성능 근거로 사용하면 안 된다. 문서에는 §6의 과거 threshold 결과와 §7의 새 linking agent 결과가 구분되어 있지만, 파일명만 보면 혼동 가능성이 크다.

## 7. 통제·추적 가능성

긍정적인 통제는 다음과 같다.

- 각 에이전트에 턴·방문·상호작용·링크 수 제한이 있다.
- 도구 계층에서 위험 행동과 잘못된 인용·selector·filter를 거절한다.
- `agent_trace`, `stop_reason`, coverage gap, blocked reason이 상태와 보고서에 남는다.
- LangGraph checkpoint로 중간 상태를 보존한다.
- 모델·네트워크 실패 시 가능한 범위에서 사람 검토 또는 fallback으로 내린다.

하지만 checkpoint는 실행 복구와 감사 추적용 상태이지, 에이전트가 과거 실패에서 스스로 학습하는 장기 메모리는 아니다. 저장된 site rule 재사용도 학습이라기보다 검증된 자동화 캐시다.

## 8. 감사 발견사항

### A-01 — 실제 bounded tool agents가 존재함

- 심각도: 정보
- 결론: “키워드 기반 시스템을 에이전트로 위장”했다는 가설은 기각
- 근거: 모델 생성 tool call, multi-turn feedback, 실제 실행별 상이한 trace, 도구 거절 후 재행동

### A-02 — 서비스 전체를 자율 에이전트로 표현하면 과장

- 심각도: 중간
- 결론: 상위 그래프·라우팅·재시도는 고정이며 대부분의 판단 노드는 단발 구조화 호출
- 권고 표현: “bounded agentic subflows inside a deterministic review workflow”

### A-03 — agentic 성능은 아직 운영 신뢰 수준을 입증하지 못함

- 심각도: 높음
- 결론: 페이지 탐색 7개 중 4개 조사 불충분, 사례 연결 recall 35.7%, 4개 중 3개 턴 한도, 추출 안정성 낮음
- 영향: agentic 구현의 진위와 별개로 결과 완전성·재현성이 부족

### A-04 — 규칙·키워드가 사용되지만 대부분 guardrail·측정·후보 생성 역할

- 심각도: 정보
- 결론: 키워드 분류기는 평가 기준선에만 존재. 다만 페이지 coverage 후보는 정규식 신호에 의존하므로 신호 밖 표현을 놓칠 수 있음

### A-05 — 평가 명칭과 현재 구현 사이 혼동 위험

- 심각도: 중간
- 결론: `agentic_eval.py`의 사례 평가는 현재 linking agent가 아님. 과거와 현재 결과를 명시적으로 versioning할 필요가 있음

### A-06 — 사람 검증이 부족함

- 심각도: 높음
- 결론: human comprehension·유해 비유 평가는 미실시이고, 사례 연결 gold도 AI 초안. 법률·금융 검토 서비스의 품질 주장 근거로는 부족

## 9. 권고사항

1. **대외 표현을 한정한다.** “AI agent가 전체 검토를 자율 수행” 대신 “고정 검토 그래프와 검증 규칙 안에서 페이지 탐색·사례 조사를 수행하는 제한형 에이전트”라고 쓴다.
2. **요청별 agenticity를 노출한다.** 보고서에 `discovery: reuse|agent`, `case_link: skipped|agent`, `persona_select: default|agent`, 각 tool turn 수를 요약한다.
3. **현재 세대 평가를 분리한다.** `agentic_eval.py`의 과거 reference 평가를 이름 변경하거나 제거하고, 결과 메타데이터에 구현명·commit·prompt hash·gold version을 기록한다.
4. **사람 라벨 평가를 우선한다.** 다양한 카드사·페이지 구조·동의어·다상품 언급·비정상 DOM을 포함하고, 최소 2인 교차 검토로 수집 completeness와 사례 연결 precision/recall을 측정한다.
5. **실패도 정식 결과로 관리한다.** 비용 한도, 턴 한도, 차단된 control, 미해결 gap을 성공률 분모에 포함하고 “일부 결과 생성”을 완료로 세지 않는다.
6. **자율성을 늘리는 것보다 실패율을 낮춘다.** 이 도메인에서는 고정 법규 매핑과 코드 검증이 장점이다. 상위 planner를 추가하는 것보다 페이지 tool coverage, 사례 검색 query 비용, 반복 제출 탈출 조건을 개선하는 편이 안전하고 측정 가능하다.

## 10. 검증 내역과 한계

이번 감사에서 다음을 수행했다.

- 소스의 그래프, 모든 모델 호출 지점, 세 도구 루프, 규칙·정규식·threshold 경로를 정적 추적
- 최신 저장 평가 결과와 `data/live3/checkpoints.sqlite`의 실제 tool trace 대조
- 관련 테스트 실행: **85 passed, 2 deselected**
- 관련 소스 lint 실행: **All checks passed**

새로운 유료 모델 호출이나 외부 사이트 재방문은 하지 않았다. 실효성 수치는 저장된 2026-09-29 실행에 의존한다. 표본이 작고 일부 fixture/gold가 로컬·gitignored이며 사람 검증이 부족하므로, 본 보고서는 **구현이 실제 agentic인지**는 높은 확신으로 판정하지만 **그 에이전트가 충분히 정확한지**는 확정하지 않는다.

## 최종 판정문

> 이 서비스에는 실제 모델 주도 도구 선택과 피드백 반복이 구현되어 있으며, 단순 규칙·키워드 탐지를 agent처럼 포장한 시스템은 아니다. 그러나 agentic 동작은 페이지 탐색·사례 연결·자유 서술 독자 선택에 국한되고, 전체 업무 계획과 판정 흐름은 고정 코드가 지배한다. 현재 명칭은 **검증 규칙을 갖춘 bounded-agent hybrid**가 적절하며, 실페이지 성공률·사례 연결 정확도·재현성·사람 평가가 개선되기 전에는 “자율 금융공시 검토 에이전트” 수준의 품질 주장을 해서는 안 된다.
