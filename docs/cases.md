## sqlite-vec 문법을 어떻게 확정했는가

기억에 의존하지 않고 설치된 `sqlite-vec==0.1.9`에 직접 물어 확인했습니다(`SELECT vec_version()`이
`v0.1.9`를 돌려줍니다).

| 확인한 것 | 결과 |
|---|---|
| 벡터 테이블 생성 | `CREATE VIRTUAL TABLE t USING vec0(key TEXT PRIMARY KEY, embedding float[N] distance_metric=cosine)` |
| 벡터 쓰기 | `sqlite_vec.serialize_float32(list[float])` |
| KNN 조회 | `WHERE embedding MATCH ? AND k = ?` — `k`나 `LIMIT`이 없으면 `OperationalError`로 거부됩니다 |
| 메타데이터 프리필터 | 같은 `WHERE`에 `AND col = ?`, `AND col IN (...)`, `AND key IN (SELECT ...)` 모두 동작합니다 |
| `k`가 행 수보다 클 때 | 오류 없이 있는 행만 돌려줍니다 |
| 코사인 거리 | 0이 동일, 1이 무관. `similarity`는 `1 - distance`로 계산해 돌려줍니다 |

`IN (SELECT ...)`이 프리필터로 동작하는 것을 확인했기 때문에, 벡터 테이블은 사례당 한 행만 두고
상품유형 필터는 `case_product_types` 서브쿼리로 겁니다. 사례마다 상품유형이 여러 개여도 벡터를
복제하지 않습니다.

## 그래프 배치

```
classify_type ─┬→ search_cases → judge_display_method → …
               └→ END   (범위 밖 / 판정 불가)
```

`route_after_classify`가 `"judge_display_method"` 대신 `"search_cases"`를 돌려주고,
`search_cases → judge_display_method`는 고정 엣지입니다.

이 자리를 고른 이유는 **사례 조회가 판정의 입력이지 결과가 아니기 때문**입니다. 판정 노드보다
뒤에 두면 이미 내려진 판정을 사례가 바꿀 수 없고, 다시 판정하려면 루프가 하나 더 필요합니다.
`classify_type` 직후에는 아직 `product_page.html`이 전처리만 끝난 상태라 질의가 상품유형·상품명
수준일 수밖에 없는데, 이 한계는 질의를 루브릭 영역별로 나눠(`QUERY_AREAS`: 의무표시·표시방법·
금지행위·설명의무) 각 영역이 상위 k에서 서로를 밀어내지 않게 하는 방식으로 덮었습니다.

`search_cases`는 재시도 대상이 아닙니다(`graph/retry.py`의 `RETRYABLE`에 넣지 않았습니다).
검증 피드백으로 달라질 것이 없는 조회이므로 다시 돌릴 이유가 없습니다.

## 이번 단계의 한계

**`case_search`를 채우는 것까지가 이번 범위입니다.** `judge_display_method`와
`judge_explanation_duty`의 프롬프트는 `case_search.hits`를 아직 읽지 않습니다. 즉 사례는 State에
쌓이고 체크포인트에 남지만 판정 근거로 쓰이지는 않습니다. 두 노드의 판정 로직 자체가 다른 작업으로
채워지는 중이어서 경합을 피한 것이기도 합니다.

연결할 때 쓸 자리는 이미 준비되어 있습니다. 각 hit의 `related_checklist`가 그 사례가 어느 루브릭
항목과 관련되는지 알려주므로, 판정 노드는 자신이 다루는 코드에 걸린 사례만 골라 프롬프트에 넣을 수
있습니다(`load_cases(db_path, codes=(...))`도 같은 일을 DB 쪽에서 합니다).
